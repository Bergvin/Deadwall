# DeadWall

Isometric dark-fantasy zombie fortress survival game that runs in the browser. The player builds walls, recruits heroes who stand on the walls, and survives endless zombie waves. If the fortress gate falls, the run is over.

- **Full game spec:** [docs/spec.md](docs/spec.md). It is long, so read only the section you need (sections are numbered 1–20).
- **Repo:** https://github.com/Bergvin/Deadwall (branch `main`)
- **User:** Bergvin. Talk to them in **Icelandic**. Code, comments, and commit messages are in **English**.

## Technical decisions (already made)

- **Three.js + Vite**, plain JavaScript (ES modules), no backend. Three.js comes from npm, not a CDN.
- **2D logic, 3D rendering:** All gameplay (grid, pathfinding, combat, waves, economy) is plain JS on a 2D grid and does not depend on Three.js. Rendering is a separate layer: an orthographic camera at an isometric angle draws the game state.
- **Models:** CC0 low-poly glTF/GLB models from Kenney and Quaternius (see the asset map below). No procedural Canvas drawing of characters.
- **Audio:** generated in code (WebAudio), or CC0 sounds.
- **Persistent data:** `localStorage`, always validated, and the game must start even if a save is corrupted.

## Design decisions (approved by the user)

These fill gaps the spec leaves open:

- **Heroes can fall:** at 0 HP a hero is "fallen" (not deleted). They can be revived for gold during the next prep phase. Warn when a hero's HP is low.
- **Building during waves is allowed:** construction and repair cost **+25%** while a wave is active.
- **Starting layout:** only the castle and the gate. The player builds every defensive line.
- **Map:** fixed, about **30×24** cells, fits on screen with light zoom.
- **No victory condition:** endless waves, the goal is a personal best. Milestone markers at waves 10, 20, 30, …
- **Repositioning takes time:** the hero walks to the new spot for a few seconds and does not attack meanwhile.
- **Hero names:** random medieval names, e.g. "Aldric the Archer".
- **Towers + one hero (redesign, approved):** the main firepower is elemental towers (fire/earth/wind/water, plus the **Rolling Stone Tower** that rolls a ball down a line and scatters what it hits) built on top of walls, one per wall, levels 1–3 bought with gold. One hero per run, 2× size (`CHAMPION` in config/towers.js), standing on a **2×2 block of walls**.
- **Hero build (Oct 2026 rework, approved, "make it crazy, balance second"):** no classes. The player picks a **starting weapon** (bow, crossbow, staff, flasks, sword, mace = the old class configs, now weapon *styles*); the weapon decides how the hero attacks and looks. The hero starts with **no abilities**; **every level gives a pick of 3 random abilities** (rarity per card, synergy-weighted), **chosen between waves** (picks pile up during a wave). ~50 abilities: stats, elements (fire/poison/frost/lightning) with synergies that require a tag (Wildfire, Inferno, Shatter, Deep Freeze, Plague Bloom, Thunderlord...), projectile mechanics (pierce, twin shot, **bounce**, **split**, fractal shards, storm of steel), melee mechanics (cleave, **long reach**, **whirlwind**, earthshaker), the old class actives (Fireball, Multishot, Shield Bash...) plus new physics actives (Shockwave, Hurricane), and broken-on-purpose mythicals. **Weapons and gear drop during the run** (mostly elites and bosses) into a bag and are equipped between waves; legendary+ weapons grant an ability. Some imbalance is welcome: finding an overpowered combo is part of the fun.
- **Physics:** hits can knock zombies back, blasts fling them outward, whirlwinds/hurricanes throw them into the air away from the gate; flying zombies sail over walls and take fall damage; zombies collide and never fully overlap. Repeated shoves weaken (resistance stacks), and stragglers alive 40 s after a wave's last spawn become **enraged** (faster, immune to knockback) so juggling can never stall a wave.
- **Rarities:** six tiers everywhere (common, uncommon, rare, **epic**, legendary, mythical), in `config/rarities.js`.
- **Wave variants:** besides normal waves there are **Swarm** waves (many fast, frail walkers/runners, poured in quickly, half gold each) and **Chubby** waves (few brutes/siege/plague with much more HP, slow spawning, more gold each). Waves 1-2 and boss waves are always normal; a special never repeats back to back; the HUD preview names the next wave's variant.
- **Hero pacing:** max level 100, about 2 levels per wave. XP is each kill's XP shared by damage (no XP per point of damage, so a strong build cannot snowball its own levels) plus a share of a level per cleared wave.
- **Difficulty:** a commander **without upgrades should usually fall around wave 5** (a lucky build may run much further, which is fine); commander levels, skills and artifacts are what carry runs further. Enemy HP grows **exponentially** late (`WAVE_TABLE.hpGrowthExp`) because the hero build stacks multiplicatively. Last simulation (6 runs each, mixed strategy): fresh avg ≈ 10 (mostly 4-5, one 31), mid ≈ 30, strong 42+.
- **Commander (meta progression between runs):** the player is the Commander. Every finished run gives commander XP (abandoned runs give none). Each commander level offers a choice of **3 random options**, each rolled with its own rarity (common, uncommon, rare, legendary, mythical): stat perks or **skills** (automatic abilities, uncommon+). Higher rarity = stronger; taking the same again stacks. No upgrade tree. Bonuses are deliberately big.
- **Artifacts:** after every finished run the player **chooses 1 of 3 artifacts**; the further the run got, the better the rarity odds (short runs give mostly commons). Common artifacts only give a small stat bonus; **uncommon and better also give an automatic ability**. Two identical artifacts (same kind and rarity) **merge** into a higher level (max 5). Limited slots (2, +1 at commander level 4, 8, 14, 20); salvage unwanted ones for XP. **Auto-salvage** (commander setting `autoSalvage: {on, keep: [rarity]}`, toggled in the Stash header): chosen artifacts of a rarity not kept are salvaged for XP at once; a two-click button clears unkept ones already in the stash (equipped ones are never touched). No artifacts drop during a run (the earlier Wanderer creatures were removed).

## Architecture rules

- All gameplay numbers (hero, wall, and zombie stats, costs, wave formulas) live in **`src/config/`**. No magic numbers in the systems.
- One system per file, kept small: e.g. `grid.js`, `pathfinding.js`, `waves.js`, `economy.js`, `combat.js`, `render/…`, `ui/…`.
- Simulation uses a fixed timestep driven by elapsed time. Pause and game speed only affect the simulation clock.
- Each entity has a unique `id`. Death and reward are triggered **once** (an `alive` flag is checked before everything).
- Every purchase goes through one function in `economy.js` that validates the balance.

## Saving tokens (important)

- **Never read binary files** (`.glb`, `.gltf`, `.png`, `.zip`). List file names with `ls` if needed.
- Read only the file or section that matters. Do not read all of `docs/spec.md` at once.
- **Test with code, not screenshots:** `window.debug` functions (spawn enemies, break a wall, add gold, jump to wave N) and Node tests for logic (`npm test`). Use screenshots only to check appearance.
- Keep a balance simulation in Node (run N waves without graphics) instead of playing manually.

## Phase 0 findings (spike, removed after phase 1 — see git history `a5e535a`/`2d9fd44`)

- Measured on the user's PC (RTX 3080) with `debug.bench()` (synchronous frames + GPU sync, valid when the tab is hidden):
  0 zombies 1.3 ms/frame · 50 → 5.6 ms · 200 → 16.4 ms (~60 fps) · 400 → 32 ms (~30 fps).
- Cost is ~0.075 ms per skinned zombie and is **per-object CPU/driver overhead**, not triangles or shadows (shadows on/off made no difference). Each `Zombie_Basic` clone has 2 skinned meshes (body 7.6k tris + eyelid) and 50 bones.
- Updating mixers every other frame (`?anim=2`) halves the update cost (3.2 → 1.9 ms at 200) but barely changes the total frame time.
- **Solved with a baked instanced horde** (`src/render/bakedHorde.js`). At load, each clip is sampled at 30 fps, and skinned positions and normals go into float textures (~90 ms for 4 clips). One `InstancedMesh` per zombie type then reads the frame per instance in the vertex shader (`aFrame` attribute + `gl_VertexID`). Result: 200 zombies **2.0 ms** (was 16.4), 1000 → 3.1 ms, 2000 → 5.2 ms. **Use this for all zombie types.** Heroes stay normal skinned meshes (few of them, and they need blended animations).
- Baked limits: no blending between clips (instant switch), one frame per instance (no interpolation; fine at 30 fps), the eyelid mesh is dropped. Shadows work via a patched `customDepthMaterial`.
- **Model units:** Kenney castle pieces are about 1 unit per cell, so scale the whole kit by one factor taken from `wall.glb`. Quaternius RPG heroes are ~3 units tall and zombies ~1.2, so normalize each by height. Models face +z, so rotate π to face north (−z). Kenney `gate.glb` is only the door leaf, so use `wall-doorway.glb` for the gate opening.
- **Camera:** yaw 0° (walls horizontal, enemies from the top of the screen), **pitch 55°** by default. Camera angle has no measurable effect on performance. Top-down (90°) works, but characters turn into blobs. Fog must start past the map center (camera distance + 4), otherwise the whole scene goes dark.

## Commands

- `npm run dev` starts the Vite dev server on http://localhost:5173 (the in-app browser preview config is in `.claude/launch.json`, name `deadwall`).
- `npm run build` writes the production build to `dist/`.
- `npm test` runs the Node tests in `tests/*.test.js` (logic only, no browser).
- `node tools/inspect-model.cjs <file.gltf|glb>…` prints meshes, skins, textures and animation names without dumping binary data.
- `tools/patch.cjs <file>` reads `[[old, new], ...]` JSON on stdin and replaces each exactly once (fails loudly if missing). Use it via Python (`subprocess` + `json.dumps`) for multi-line edits; avoid `node -e` with template literals in Bash (backticks get eaten). `sed -i` replaces files in a way Vite's watcher on Windows can miss; if the dev server serves stale code, restart it.
- CSS class names for floaters must not collide with UI classes (e.g. `.ability` styles the ability buttons).
- `node tools/simulate.js [runs] [none|walls|fire|earth|wind|water|mixed|all] [maxMinutes]` plays headless runs with scripted strategies (champion block + rings of walls around the gate, towers, upgrades, talents, repairs) and prints the wave reached. `COMMANDER=fresh|mid|strong` plays with a commander profile (defined in the script). Targets: fresh mixed ≈ 4-5 (walls ≈ 3, fire ≈ 5), mid ≈ 11-12, strong ≈ 40. `LEVELS=1` also prints the hero's level after every wave (target: about 2 per wave). `BUILDS=1` prints each run's final weapon and abilities and which abilities show up in above-average runs (spot overpowered combos). The script hero takes the highest-rarity pick (synergy first) and wears higher-rarity drops. Re-run after any balance change and update docs/acceptance.md.
- In the browser console: `debug.state()`, `debug.newGame(seed)`, `debug.sim()`, `debug.build(x, y)`, `debug.buildLine(x0, y0, x1, y1)`, `debug.sellAt(x, y)`, `debug.addGold(n)`, `debug.spawn(type, x, y, n)`, `debug.hero(type, x, y)` (recruit + deploy; note `grid.wallAt` returns a wall id), `debug.damageWall(x, y, n)`, `debug.damageGate(n)`, `debug.fastForward(seconds)`, `debug.screenOf(x, y, h)` (cell → client pixel, for simulated clicks), `debug.cellAt(cx, cy)`, `debug.commander()`, `debug.commanderXp(n)`, `debug.giveArtifact(id, rarity)`, `debug.artifactOffer(wave)`, `debug.loot(slot, rarity, style)`, `debug.grant(abilityId, rank)`, `debug.heroXp(n)`.
